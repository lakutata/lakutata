# Internationalization (i18n)

`lakutata/com/i18n` (the `@lakutata/i18n` package) manages the messages of each language by their **keys**: the code
uses a key, and each language gives the sentence of the key in its own file. The messages use the syntax of
[ICU MessageFormat](https://unicode-org.github.io/icu/userguide/format_parse/messages/); their numbers, currencies, dates
and plurals are formatted in their language by the `Intl` of Node.js, with no third-party library.

## The files of the messages

A JSON file by language, named by its language tag (BCP 47: `en`, `zh-CN`, `zh-Hant-TW`):

```
locales/
  en.json
  zh-CN.json
```

```json
{
  "order": {
    "count": "{count, plural, =0 {No orders yet} one {# order} other {# orders}}",
    "created": "Order created for {customer}"
  }
}
```

The nesting of the JSON is the one of the keys: the keys above are `order.count` and `order.created`. A part of a key
cannot contain `.`.

A language can also be a directory, the names of its files (and of their directories) prefixing their keys:

```
locales/
  zh-TW/
    order.json         → order.*
    admin/user.json    → admin.user.*
```

Both layouts can be mixed in a directory.

## Configuration

```ts
import {Application} from 'lakutata'
import {BuildI18nOptions} from 'lakutata/com/i18n'

Application
    .alias({'@locales': '/path/to/locales'})
    .run(() => ({
        id: 'shop',
        name: 'Shop',
        components: {
            i18n: BuildI18nOptions({
                directory: '@locales',               //an alias, or several directories
                defaultLocale: 'en',                 //the default language, the last fallback (en by default)
                fallback: {'zh-TW': 'zh-CN'},        //the messages missing in zh-TW are the ones of zh-CN
                currency: 'CNY',                     //the currency of {price, number, currency}
                timeZone: 'Asia/Shanghai'            //the time zone of the dates and the times (the process's by default)
            })
        }
    }))
```

The messages can also be given in the code instead of a directory: the `messages` option gives them by language, as
object literals or imported JSON. They are then bundled with the code (`lakutata package bundle`), no file read at run time:

```ts
import en from './locales/en.json' with {type: 'json'}
import zhCN from './locales/zh-CN.json' with {type: 'json'}

BuildI18nOptions({
    messages: {
        'en': en,
        'zh-CN': zhCN,
        'ja': {order: {created: '{customer} の注文を作成しました'}}
    }
})
```

| Option | Description |
|---|---|
| `directory` | The directories of the messages; aliases accepted |
| `locales` | The supported languages; the languages loaded (and the default one) by default |
| `defaultLocale` | The default language, `en` by default |
| `fallback` | The languages a message missing in a language is looked up in next |
| `messages` | Messages by language given in the code, loaded after the directories (the same keys replaced); no `directory` is needed with them |
| `missing` | A missing message or argument: `'throw'` throws; `'key'` gives its key (the argument as `{name}`) and warns once. Thrown by default, the key given when `NODE_ENV=production` |
| `currency` | The currency when neither the message nor its arguments give one (ISO 4217) |
| `timeZone` | The time zone of the dates and the times (IANA) |
| `validationMessages` | Whether the built-in validation messages of the supported languages are registered, `true` by default (see "The errors of the validation") |

## Usage

```ts
import {Inject} from 'lakutata/decorator/di'
import {type I18n} from 'lakutata/com/i18n'

class OrderService extends Provider {
    @Inject('i18n')
    protected readonly i18n: I18n

    public summary(count: number, locale: string): string {
        return this.i18n.t('order.count', {count: count}, locale)
    }
}
```

| Method | Description |
|---|---|
| `t(key, params?, locale?)` | The message of a key in a language, formatted with its arguments; the default language by default |
| `has(key, locale?)` | Whether a language (or the ones it falls back to) has a key |
| `format(message, params?, locale?)` | Format an ICU message which is not in the files |
| `translator(locale)` | A translator of a language (`ITranslator`), which does not need the language each time |
| `negotiate(requested)` | The supported language for the requested ones (preferred first), the default one when none is supported |
| `addMessages(locale, messages)` | Add messages of a language at run time, the same keys replaced |
| `getLocales()`, `getDefaultLocale()`, `getKeys(locale)` | The supported languages, the default one, the own keys of a language |

### Answering a request in its language

With the `I18nMiddleware` on the entrypoint, each request has its language; the objects of the request inject the
`Translator`, the messages of that language:

```ts
import {BuildEntrypoints, Controller} from 'lakutata/com/entrypoint'
import {CLIAction, GET} from 'lakutata/decorator/ctrl'
import {Inject} from 'lakutata/decorator/di'
import {BuildI18nOptions, I18nMiddleware, Translator} from 'lakutata/com/i18n'

class OrderController extends Controller {
    @Inject(Translator)
    protected readonly i18n: Translator

    @GET('/orders/count')
    @CLIAction('count-orders')
    public async count(): Promise<string> {
        return this.i18n.t('order.count', {count: await this.countOrders()})
    }
}

Application.run(() => ({
    components: {
        i18n: BuildI18nOptions({directory: '@locales'}),
        entrypoint: BuildEntrypoints({
            controllers: [OrderController],
            middlewares: [I18nMiddleware],
            http: ExpressHTTPEntrypoint({port: 3000})
        })
    }
}))
```

The languages a request asks for are read in this order, then negotiated with the supported ones (see below), the
default language when none is supported:

| Entrypoint | Sources (preferred first) |
|---|---|
| HTTP (Express, Fastify) | The query parameter `?lang=`, the cookie `lang`, the `Accept-Language` header |
| Socket.IO | The query parameter `lang`, the cookie `lang` and `Accept-Language` of the connection |
| Command line | The environment variables `LC_ALL`, `LC_MESSAGES`, `LANG`, then the language of the process |
| Electron IPC | The environment and the language of the main process |
| Schedules | None (the default language) |

- The objects of a request (the controller, the `@Scoped` providers, the access control rules) inject the same
  `Translator`; `translator.locale` is the language of the request, so is `context.locale`.
- The middleware uses the component named `i18n`. To use another one, other names of the query parameter or of the
  cookie, or another way to choose the language (the one saved by the signed-in user), extend `I18nMiddleware`:

  ```ts
  class LanguageMiddleware extends I18nMiddleware {
      @Inject('lang')
      protected readonly i18n: I18n

      protected readonly queryParameter: string = 'locale'

      protected requested(context: BaseContext): string[] {
          return [...this.userLanguages(context), ...super.requested(context)]
      }
  }
  ```

- The `Translator` of a request without the `I18nMiddleware` throws an `I18nTranslatorException`.
- A translator (the `Translator`, and the `ITranslator` of `translator(locale)`) has `locale`, `t(key, params)`,
  `has(key)`, `format(message, params)`, `number(value, options)` and `date(value, options)`.
- Out of a request (the schedules, the singleton components), the component gives `t(key, params, locale)` and
  `translator(locale)`.
- To handle the languages yourself, `ParseAcceptLanguage(header)` reads `Accept-Language` and `EnvironmentLocales()`
  the languages of the environment (`zh_CN.UTF-8` becomes `zh-CN`), for `negotiate()`.

## The help and the prompts of a command line tool

The `translate` option of the Commander adapter (`lakutata/adapter/commander`) gives the help and the prompts of a
command line tool in the language of the user: the descriptions of the program and of its commands, of their arguments
and options, the hints of the defaults and of the choices, the titles of the help (Usage:, Options:), the descriptions
of `--help` and `--version`, and the questions asked for the missing required options. The names of the commands and of
the options are not translated.

`CommanderTranslator()` translates them with the messages of an i18n component:

```ts
import {BuildEntrypoints} from 'lakutata/com/entrypoint'
import {CommanderCLIEntrypoint} from 'lakutata/adapter/commander'
import {BuildI18nOptions, CommanderTranslator, I18nMiddleware} from 'lakutata/com/i18n'
import zhCN from '../locales/zh-CN.json' with {type: 'json'}

components: {
    i18n: BuildI18nOptions({messages: {'zh-CN': zhCN}}),
    entrypoint: BuildEntrypoints({
        controllers: [ExampleController],
        //The Translator of the controllers running the commands has the same language
        middlewares: [I18nMiddleware],
        cli: CommanderCLIEntrypoint({bin: 'tool', translate: CommanderTranslator()})
    })
}
```

```json
{
  "cli": {
    "description": "示例工具",
    "commands": {
      "greet": {
        "description": "问候某人",
        "arguments": {"name": "被问候的人"},
        "options": {"times": "次数"}
      }
    },
    "help": {"usage": "用法：", "options": "选项：", "default": "默认：{value}", "hints": "（{hints}）", "separator": "，"}
  }
}
```

- The keys (prefixed by `cli.` by default, the `prefix` option changes it):
  - the program: `description`; the commands: `commands.<command>.description`, `commands.<command>.arguments.<name>`,
    `commands.<command>.options.<property>`;
  - the help: `help.usage`, `help.arguments`, `help.options`, `help.commands`, `help.helpOption`, `help.helpCommand`,
    `help.versionOption`;
  - the hints: `help.default` (`default: {value}`), `help.choices` (`choices: {choices}`), `help.hints` (` ({hints})`,
    the hints after a description), `help.separator` (`, `), `help.negate` (`Turn off {flag}`);
  - the questions: `prompt.json` (`Not a JSON object`).
- A text without a message is the English one of the code: only the other languages need messages.
- The language is the one of the environment variable of the `environment` option, of `LC_ALL`, `LC_MESSAGES`, `LANG`,
  then the one of the process.
- The wide characters (Chinese, Japanese, Korean) take two columns: the long lines of the help are wrapped between them,
  no punctuation starting a line.
- `translate` can be given a function too: `translate: () => (text) => messages[text.key] ?? text.text`.

## The errors of the validation

With the `I18nMiddleware`, the errors of the validations of a request are in the language of the request: its input
(the DTO of `@HTTPAction`, `@CLIAction`, `@ServiceAction`), the arguments and the results of the methods it calls
(`@Accept`, `@Return`), and the validations of its code (`DTO.validate`, `DTO.validateAsync`).

The validation messages of 20 languages are built in; the component registers the ones of its supported languages when
it starts (the languages used only are loaded):

`en`, `zh-CN`, `zh-TW`, `ja`, `ko`, `fr`, `de`, `es`, `pt-BR`, `it`, `nl`, `pl`, `ru`, `uk`, `tr`, `vi`, `th`, `id`, `hi`, `ar`

A supported language uses the closest built-in one: `zh`, `zh-Hans`, `zh-SG` use `zh-CN`; `zh-Hant`, `zh-HK`, `zh-MO`
use `zh-TW`; the others match by their language (`pt-PT` uses `pt-BR`, `fr-CA` uses `fr`). A language without built-in
messages uses the ones of the languages it falls back to, then English.

An application replaces or adds validation messages in its messages: under `validation`, by the codes of the errors, in
the syntax of the templates of the validation (`{{#label}}`, `{{#limit}}`), not ICU:

```json
{
  "validation": {
    "any": {"required": "Please enter {{#label}}"},
    "string": {"min": "{{#label}} needs {{#limit}} characters at least"}
  }
}
```

- The validation messages of a language are layered: the built-in and the application messages of the languages it
  falls back to, then its own built-in and application messages, the later ones replacing the earlier ones.
- `validationMessages: false` registers no built-in messages, the `validation` messages of the application only.
- The input of a request is validated as before; only an invalid input is validated again in the language of the
  request, for its messages. A valid input is not affected at all.
- A few messages contain English given by the validation itself: the sort order (`ascending`), the reason of a
  reference error, the message of a custom assertion. These parts stay in English in every language.
- Without the i18n component, the functions of `lakutata` do it: `LoadValidationMessages(language)` loads the built-in
  messages of a language, `RegisterValidationMessages(language, messages)` registers them, and a validation gives them
  with its `{errors: {language}}` option, or `RunInValidationLanguage(language, fn)` gives the language to every
  validation of a code (its asynchronous calls too).

## The messages of the exceptions

With the `I18nMiddleware`, an exception thrown by a request whose message is in the messages of the application is
given the message in the language of the request: its key is `errors.<the errno of the exception>`, formatted with the
parameters of the template of the exception:

```ts
class OrderNotFoundException extends Exception {
    public errno: string = 'E_ORDER_NOT_FOUND'
}

throw new OrderNotFoundException('Order {id} not found', {id: 7})
```

```json
{"errors": {"E_ORDER_NOT_FOUND": "订单 {id} 不存在"}}
```

- A request in Chinese gets `订单 7 不存在`, a request in English the original `Order 7 not found`; the `errno` and
  the other properties are not changed.
- The parameters given one by one (`new XxxException('{0} of {1}', a, b)`) are `{0}`, `{1}` in the message.
- An exception without a message is as it is; so is one whose message cannot be formatted (a missing parameter), with a
  warning.
- Out of a request, `ExceptionParams(exception)` gives the parameters of an exception, to translate it.



## Negotiation and fallbacks

**Negotiation** (`negotiate`): for each requested language in turn, the same tag, then its language alone
(`en-GB` → `en`), then another region of its language (`pt-PT` → `pt-BR`, in the order of the supported languages); the
default language when none matches.

**Fallbacks**: a message missing in a language is looked up in the languages of its `fallback`, then in the tags it is
more specific than (`zh-Hant-TW` → `zh-Hant` → `zh`), then in the default language. A message is always formatted in
the **language asked**: an English message falling back in a German request still writes `1.000`.

## The syntax of the messages

| Syntax | Example |
|---|---|
| Argument | `Hello, {name}` |
| Number | `{n, number}`, `{n, number, integer}`, `{n, number, percent}` |
| Currency | `{price, number, currency}` (the currency of the `currency` argument or of the configuration), `{price, number, currency/EUR}` |
| Date, time | `{at, date, short}`, `{at, time, long}`, styles `short`, `medium`, `long`, `full`; a `Date`, a timestamp, a date string or an object with `toDate()` |
| Plural | `{count, plural, =0 {none} one {# item} other {# items}}`: the `=value` first, then the plural rules of the language; `#` is the number formatted; `offset:1` supported |
| Ordinal | `{place, selectordinal, one {#st} two {#nd} few {#rd} other {#th}}` |
| Select | `{role, select, admin {Administrator} other {User}}` |
| Quoting | `''` is an apostrophe; `'{literal}'` writes the braces (`'#'` writes `#` in a plural) |

`plural`, `selectordinal` and `select` need an `other` option. A message is parsed once, when it is first used; a syntax
error tells its language, its key and its position, e.g. `zh-CN: order.count: the "other" option is required at 1`.

## The types of the keys

An application can declare its keys and their arguments: a wrong key or a missing argument is then an error of the
compilation. `lakutata i18n types` generates the declaration from the messages of the default language (see below), or
it is written by hand:

```ts
declare module 'lakutata/com/i18n' {
    interface I18nMessages {
        'order.count': { count: number }
        'order.created': { customer: string }
    }
}
```

Without them, `t()` accepts any key and any arguments.

## The command line tools

The `lakutata` command line (`@lakutata/cli`) handles the directories of the messages (`--dir`, `locales` by default;
several separated by commas):

| Command | Description |
|---|---|
| `lakutata i18n check` | Checks the messages of the languages against the default language (`--default`, `en` by default). Errors: a syntax error of ICU, a key the default language does not have, an argument the default message does not have, an unknown validation code or a variable of another code; warnings: a missing message (falling back), an argument not used, a message the same as the default one (not translated yet). It fails on the errors, on the warnings too with `--strict`, for the CI |
| `lakutata i18n types` | Declares the keys of the messages of the default language and their arguments (`--out`, `src/i18n.d.ts` by default); `--module @lakutata/i18n` for the applications importing `@lakutata/i18n` |
| `lakutata i18n add <locale>` | Adds a language made of the messages of the default language (a file or a directory, as the default language has; its `validation` part left, the language having its built-in validation messages), to be translated |

The checks are functions of the code too: `LoadCatalogs(directories)`, `CheckCatalogs(catalogs, defaultLocale)`,
`GenerateMessageTypes(catalogs, defaultLocale)`.

## Exceptions

| Exception | When |
|---|---|
| `I18nCatalogException` | An invalid file or configuration: invalid JSON, a file name which is not a language tag, a missing directory, an alias not resolved |
| `I18nMessageSyntaxException` | The syntax of a message is wrong |
| `I18nMissingKeyException` | A key is missing (`missing: 'throw'`) |
| `I18nMissingParameterException` | An argument is missing (`missing: 'throw'`), or a currency message has no currency |
| `I18nTranslatorException` | The `Translator` of a request without the `I18nMiddleware` |
